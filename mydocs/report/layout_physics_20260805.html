1다섯 배치 모드 — 물리 상태

배치 모드는 별도 개념이 아니라 CommonObjAttr의 두 비트 축 조합이다: treat_as_char(bit0) × text_wrap(bit21–23). treat_as_char=1이면 text_wrap과 무관하게 인라인이다. parser/control/shape.rs:339-411 · float_placement.rs:27-45

2좌표계 물리 — 기준계와 공식

모든 비-TAC 개체의 좌표는 공식 하나다. 오프셋 값 자체가 아니라 기준계와 정렬이 오프셋의 의미(원점·부호 방향)를 정한다 — "값은 그대로인데 기준점이 바뀌어 튄다"는 현상의 정확한 물리. float_placement.rs:96-132 · table_layout.rs:2400-2465 · picture_footnote.rs:331-362

x = ref_x + align_adjust(h_align, ref_w, w) ± h_offset
y = ref_y + align_adjust(v_align, ref_h, h) ± v_offset

align_adjust: Left/Top → +offset  |  Center → (ref−size)/2 + offset  |  Right/Bottom → (ref−size) − offset ← 부호 반전!

  • "Char" 기준계는 없다 — treat_as_char=1이 기준계 축 전체를 대체한다(줄 인라인).
  • 크기도 기준계를 가진다: width/height_criterion이 Absolute면 HWPUNIT 절대값, 아니면 기준 영역의 raw/10000 비율. picture_footnote.rs:284-306
  • bit13 flow_with_text(=UI restrictInPage): vert=Para 개체의 y를 본문 영역으로 클램프하고, 자리차지 push-down도 이 비트가 켜져야 적용. 켜지면 allow_overlap 강제 false. table_layout.rs:2484-2524
  • 그룹 내부는 별도 좌표계: ShapeComponentAttr의 그룹-로컬 offset + 아핀 행렬(render_*). 그룹 리사이즈는 자식 불변·스케일만. 자식 점 변환에는 최상위 그룹 anchor 하나만 더한다. shape.rs:190-244 · shape_layout.rs:909-949
  • 셀 안은 기준계가 통째로 대체된다: 셀 inner_area가 Paper/Page/Column을 대신하고 horz_rel_to는 무시(horz_align만 소비), vert는 Para(=para_y) vs 그외(=셀 inner) 2분법. table_cell_content.rs:318-380
  • 글상자 내부: 원점 = 도형 좌상단 + 글상자 여백, 내부 vpos는 글상자-로컬 누적(일부 파일은 페이지 절대값이라 원점 정규화 차감). shape_layout.rs:2237-2247, 56-79

3파이프라인과 단일 진실

줄 구조의 진실은 Paragraph.line_segs 하나다. 렌더(composed.lines)는 line_segs의 파생(재생)이고, 저장·쪽분할·측정·hit-test가 모두 여기에 매달린다. 이 축을 벗어난 "손 편집"이 데싱크 버그의 최대 공급원이다.

파이프라인의 핵심 계약 5

  • 인라인/블록 게이트는 단일 함수(is_tac_table_inline_in_para)를 측정·pagination·composer·layout·typeset·paragraph_layout 6곳이 공용한다 — 판정이 갈리면 데싱크. height_measurer.rs:58 · pagination/engine.rs:1703-1717
  • 게이트(소비자)는 line_seg 증거를 따르고, 자기 줄 생산은 reflow의 몫 — 게이트가 독자 재분류하면 로드 문서의 저장 조판과 어긋난다. height_measurer.rs (2026-08-05 수리)
  • 저장 line_seg의 vpos==0(줄>0)은 "이 줄부터 새 쪽"이라는 파일 권위 신호 — fit 여부와 무관하게 단/쪽을 진행한다. typeset.rs:13272-13295 · pagination/engine.rs:1194-1228
  • typeset의 items 순서 = layout의 그리기·y 진행 순서 (y_offset 스레딩). 흐름 항목만 y를 전진시키고 overlay/Paper-절대는 전진 0. layout.rs:4471-4525
  • 선점은 등록부로 기록: 한 개체를 두 경로(paragraph_layout ↔ layout/shape_layout)가 그릴 수 있으면 set/get_inline_shape_position으로 이중 emit을 막는다. layout.rs:6131-6144 · shape_layout.rs:626-630

4흐름(flow)과 배타 밴드

본문은 y_offset 하나가 아래로 흐르는 1차원 흐름이고, 개체는 세 가지 방식으로만 개입한다: 줄 안에 산다(TAC), 흐름을 밀거나 좁힌다(밴드), 흐름 밖에 떠 있다(오버레이·절대).

  • 페이지 y 공식: 페이지 y = 컬럼 앵커 y + px(vpos − page_vpos_base). base는 페이지 첫 항목의 첫 line_seg vpos. layout.rs:1109-1160

5어울림(Square) 상세 물리

어울림은 "즉석 렌더 좁힘"이 아니라 line_segs 재기록 → 재생이다(즉석 좁힘은 양쪽정렬 압축 부작용으로 폐지). 좁힘의 결정은 렌더 위치 기반인데 좁힘 결과가 위치를 되바꾸는 닭-달걀이라, 고정점 반복 2중 루프로 수렴시킨다.

밴드 수명주기

  1. 생성: 공백 host 문단에 앵커된 float 표의 렌더트리 Table bbox(±outer margin)가 ReflowBand가 된다. x는 단(column) 로컬, y는 절대 흐름 좌표. table_ops.rs:89-118, 170-188
  2. 좁힘: 줄 구간이 밴드와 겹치면 옆 조각으로 재줄바꿈 — BothSides면 빈 구간 전부(≥34px), flow 혼재면 첫 밴드 기준 단일 조각(Left/Right/Largest, 동률은 오른쪽). line_breaking.rs:1360-1411
  3. 기록: 좁은 줄만 cs/sw(HWPUNIT)를 얻고, 같은 시각 줄의 두 세그는 같은 vpos 공유, 태그 좌=FIRST(0x20000)·우=LAST(0x40000) — 한컴 저장 형식 그대로. line_breaking.rs:1578-1630
  4. 재생: 렌더는 저장된 cs/sw를 그대로 소비(line x = col.x + margin + cs). typeset은 앵커 시그니처가 일치하는 문단을 WrapAroundPara로 흡수(높이 0). paragraph_layout.rs:3251-3292 · typeset.rs:2743-2952

6모드 전환 물리 — rebase 부재

사용자 분석("기준점 텔레포트 + 리플로우 편입")의 코드 실증. 배치 속성 변경의 물리는 두 반쪽으로 구성돼야 하는데, rhwp는 반쪽(무효화)만 있고 반쪽(좌표 rebase)이 없다.

있는 것 — 무효화 시퀀스

  • 배치 속성은 3중 기록(모델 common 필드 + attr 비트필드 + raw_ctrl_data 바이트)이어야 저장에 살아남는다 — 하나라도 빠지면 재로드 시 원복. table_ops.rs:2532-2645
  • 변경 후 표준 시퀀스: raw_stream=None → recompose_section → host reflow → square 밴드 훅 → paginate 5단계. table_ops.rs:2297-2302, 2875-2880
  • 스타일 사전이 바뀌는 편집은 rebuild_section(styles 재해석 + 전체 재조판). rendering.rs:4727-4731

없는 것 — 좌표 rebase (P0 갭)

P0rel_to/align/wrap 전환 시 오프셋 rebase 코드가 없다 apply_common_obj_attr_from_json은 열거값만 교체하고 오프셋을 그대로 둔다 — 다음 레이아웃에서 새 기준계로 재해석되어 개체가 시각적으로 점프한다. 1. 이중 진실 데싱크 금지line_segs(저장·쪽분할)와 composed.lines(렌더)는 파생 관계 — 한쪽만 바꾸면 렌더 불변 또는 조용한 부패. raw_ctrl_data ↔ common enum도 동일. tac-inline-baseline-report · composer.rs:472

8사례 연구 — 2026-08-05 실증 2건

사례 1 — TAC 표 세로정렬 붕괴 수리: 법칙 4·5·6의 실전

"왼쪽"+TAC 표에서 표가 텍스트보다 46px 위에 뜨던 버그. 이전 세션의 두 시도(게이트 단독 변경, line_seg 단독 append)는 모두 실패했는데, 이 보고서의 법칙으로 재해석하면 실패가 당연했다: 법칙 6(게이트만으론 y 불변) 위반과 법칙 1(line_seg만 바꾸면 데싱크… 로 보였으나 실제로는 composed가 파생이라 생산을 정확히 하면 자동 정합) 오진. 실제 수리는 ① 게이트에 end-anchor 분기, ② composer 생산에 자기 줄 seg, ③ createTableEx의 수동 범프 제거(법칙 5) — 3곳으로 끝났고 "4곳 일관 변경" 우려는 파생 관계 확인으로 해소됐다.

파생 수리: 양쪽정렬이 "왼쪽" 두 글자를 줄 폭으로 벌리는 회귀 → 법칙 12 신설.

사례 2 — issue_2243 결재 sliver 회귀: 법칙 8의 탄생

위 수리 직후 전체 스위트에서 로드-전용 핀(결재 HWPX, 한글 COM 쪽수 5)이 6쪽으로 회귀했다. "reflow는 편집에서만 돈다"는 가정이 틀렸다 — 기계생성 HWPX의 0높이 lineseg를 로드 때 보정하는 reflow_zero_height_paragraphs가 새 생산 코드를 실행했고, \n으로 이미 줄 구조를 명시한 문단("제목\n + 표")에 자기 줄이 하나 더 붙어 문서가 40px 부풀었다. 수리: end-anchor 계약(단일 소스 헬퍼)에 "\n 있는 문단은 대상 밖" 조건 — 강제 줄바꿈은 사용자가 명시한 줄 구조이므로 존중한다.

교훈: 생산자(composer) 변경은 반드시 로드 경로 핀(기계생성 HWPX 포함)까지 검증 범위에 넣는다.

10수리 전략 — 법칙 단위로 고치기

"하나하나 수정"이 늦어지는 이유는 증상 하나가 법칙 위반 하나에서 방사되기 때문이다. 다음 순서를 권장한다 — 각 항목이 여러 증상을 한 번에 닫는다.
