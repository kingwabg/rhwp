# parity — 한컴 정합 오라클 코퍼스

## 왜 (2026-07-27 방향 전환)
조판 의미론(어울림·표 나눔·쪽 경계…)은 공개 포맷 스펙에 **없다** — 한글 실물에만 있다.
그래서 qa:rhwp(자기일관성 검증)만으로는 한컴 정합에 도달할 수 없다는 것이 실측 결론.
정답지를 갖고 싸운 싸움(1725 PDF 242쪽, TAC 쪽수 정합 66/27/35)만 빨리 끝났다.
→ **오라클-선행 원칙**: 정답지 없는 조판 수리는 하지 않는다. 없으면 "미확정 — 한컴 확인 대기".

## 축 선정 근거
sc- 제품 코드 역산(일지·공문·평가 HWP 생성 경로): 표는 전부 **글자처럼취급(tac)**,
서식 축 = fontSize·bold·textColor·align·colWidths·병합·누름틀. 이 축이 1순위 —
"한글 전체의 100%"가 아니라 "제품 문서의 100%"가 목표다.

## 구조
```
parity/
├── fixtures/   F##_축이름.hwp — 축 하나당 파일 하나, 최소 내용 (생성: examples/gen_parity_fixtures.rs)
└── oracle/     F##_축이름.pdf|png — 한컴(한컴독스/한글)이 렌더한 정답지 (사람 손 1회)
```

## ⭐ 자동 오라클 — 사람 손·로그인 불필요 (2026-07-27 발견)
**한글이 저장한 .hwp 안에는 한글이 직접 렌더한 1쪽 그림(PrvImage)이 들어 있다.**
즉 우리가 이미 가진 실물 코퍼스가 그 자체로 정답지다 — 한컴 접속이 필요 없다.
실측: `samples/*.hwp` 268개 중 **250개 보유**.

```bash
./parity/oracle-sweep.sh 400 parity/out-full   # (한컴 1쪽 | 우리 1쪽) 짝 생성 — 250/250
node parity/compare.mjs parity/out-full        # 줄 띠 대조 스코어 (분류용 순위)
```
- 래스터화·이미지 해석은 sc- 에 이미 설치된 **sharp** 를 빌려 쓴다(새 의존성 0).
- ⚠ **PrvImage 는 낡을 수 있다**: 한글이 **마지막 저장 시점**에 만든 그림이라, 다른
  도구가 재저장한 파일에는 옛 그림이 남는다(실측: `253E164F57A1BC6934-empty` 는 본문이
  비었는데 미리보기엔 포스터). compare.mjs 가 잉크량 비(0.2~5 밖)로 자동 제외한다.
- ⚠ **점수는 정합률이 아니라 분류용 순위**다. 띠 중심 ±5px 매칭이라 육안으론 거의 같은
  문서도 54% 가 나온다(실측: `3-11월_실전_통합_2022`). **판정은 눈으로** — 점수는
  "먼저 볼 문서"를 고르는 데만 쓴다.

## 절차 (수동 오라클 — 위 자동 경로로 안 되는 축만)
1. `cargo run --release --example gen_parity_fixtures` — fixtures/ 생성
2. `cargo run --release --example smoke_parity_fixtures` — 우리 reader 재열람 스모크
3. 사람: fixtures/*.hwp 를 한컴독스(hancomdocs.com)에 업로드해 열고 캡처 → oracle/
   (제품 축 픽스처 F01~F05 는 우리가 만든 파일이라 PrvImage 가 없다 — 이 경로가 필요)

## ⚠ 픽셀 대조의 한계 — 줄 폭 검사가 따로 필요하다
위 어울림 결함은 **그림이 글자 위에 그려져 화면 대조로 안 잡힌다**(세로 띠·가로 끝 지표 모두
무력, 실측). 대신 한컴이 파일에 적어둔 줄 폭과 우리 줄 상자를 직접 비교한다:
```bash
cargo run --release --example qa_lineseg_parity        # samples/*.hwp 전수 (BIG=50 문턱 조절)
```
⚠ **작은 차이는 신호가 아니다**(교차검증으로 확인): 한컴 PrvImage 와 픽셀로 100% 일치하는
문서(`143E433F503322BD33`)도 2px 기준으론 30% 로 나온다 — `segment_width` 는 줄의 **가용 띠
폭**이지 그린 줄 상자 폭이 아니어서 표·단·들여쓰기 경로에서 정상적으로 어긋난다. 그래서
**50px 이상 큰 어긋남만** 센다(그 기준에서 위 통제 문서는 오탐 36건 → 1건). 1차 결과:
842줄 / 81,120줄 · 43파일 / 268.

**역할 분담**(중요): 픽셀 오라클(PrvImage, **1쪽만**) = 판정. 줄 폭 검사기 = 진단·회귀망.
큰 어긋남이 1쪽 밖에 있으면 지금은 **검증할 방법이 없다** — 작업 목록에 올리지 말 것.

## 스코어보드 (2026-07-27, 250건 — 밀림 보정 후)
**세로(줄 위치) 87% · 완전일치 143/237 · 가로(줄 끝) 84% · 오라클 의심 제외 12건.**

⚠ 점수를 믿기 전에 읽을 것 — 이 지표로 "결함"처럼 보인 것들을 파본 결과:
- **세로 밀림 보정 필수**: 문서가 통째로 몇 px 밀린 것과 조판이 틀어진 것은 다른데, 보정 없이
  재면 1px 밀림도 전 줄 불일치가 된다. `byeolpyo4` 는 보정 전 3% → 보정 후 **92%**(6px 밀림).
  보정 없는 옛 수치(평균 80%)는 폐기.
- **남은 밀림의 정체 = 폰트 메트릭 오차 누적**: 첫 줄은 대체로 ±2px 안에서 맞고(실측), 아래로
  갈수록 벌어진다. 본문 세로 길이 비(우리/한컴)는 0.982~1.025 로 **양방향 산포** — 단일 원인의
  체계적 오프셋이 아니다. 즉 이 잔차는 지금 구조로는 수리 대상이 아니다.
- **육안 인상도 못 믿는다**: 축소 합성 이미지에서 "번호 목록 들여쓰기가 과하다"고 판단했으나
  행별 좌측 잉크 시작을 실측하니 ±10px(글꼴 렌더 차) — 결함 아님.

**결론**: 이 지표가 실제로 잡아낸 결함은 **218px 급 총체적 오류 1건**(어울림 옆흐름)뿐이다.
소수점 추격은 수확이 없다. 1쪽 밖 검증 수단이 생기기 전까지 추가 조판 수리는 보류가 맞다.
